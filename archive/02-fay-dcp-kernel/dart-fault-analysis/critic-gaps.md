# Gaps (critic, 2026-10-09)

- G1 (most important, and no crash is needed to close it): nothing logs which allocation owned DVA 0x10fffdfc000. No log line shows a D411/D451/D452 callback or its returned DVA. That page is reachable only by the first DCP-domain allocation after the 1 MiB shmem (next-fit allocator, iova.c:184-191,215) or by rcache reuse. So the IOMFB init callback ORDER is also unknown: index order of the D411 calls, and the size of any D451/D452 before the pmgr mapping. If D411(0/1/4) (0x690000/0x800000) came first, the pmgr page cannot be at 0x10fffdfc000. One normal boot with the filtered dma:* + dcp:iomfb_callback trace decides H1 against H2/H3/H4.

- G2: the identity and arguments of mailbox #118 (crash-boot.log:1093, CB length 0x14, right after 'free_all_sdp_resources') are unknown. Candidates in the 14.7 table are D454 release_mem_desc (iomfb_v14_7.c:88), D209 get_time (:76) and D574 'power_up_dart' (:94, '[574] = trampoline_zero, /* power_up_dart */'). Linux answers D574 with a zero and does nothing. If #118 is powerUpDART(false/true) issued during power-down, the AP side may be expected to do something to the DART at exactly this point (inference). That is a candidate not covered by H1-H5. The meaning of D574 on macOS is unverified.

- G3: firmware identity is unverified. DCP runs firmware from the macOS 14.8.3 stub (/boot/asahi/stub_info.json: ProductVersion 14.8.3, 23J220; crash log 'RTKit-2419.140.12.release'). m1n1 reports it as 14.7.0: the live DT apple,firmware-version is <14 7 0>, and m1n1 src/firmware.c:151-153 has a commented-out V14_8_3 entry marked 'Same as 14.7' with the same iBoot string. The 14.7 callback/struct tables in iomfb_v14_7.c were never checked against the actual 14.8.3 DCP binary. Low probability, but everything tag-based (454/574/209) depends on it. Grepping the D-number/method-name table in the real firmware binary would settle it.

- G4: the PTE state at the fault is unknown, i.e. H1(a) vs (b). No one checked whether the kernel io-pgtable leaf at L1 0x7ff / L2 0x77f (offset 0x3bf8 in the L2 page) was valid before or after the fault. If valid, the expected value is 0x000fff002d03d003. I computed that from io-pgtable-dart.c:82-92 (PA>>4 & GENMASK(37,10)), SUBPAGE_END=0xfff, VALID, and NO_CACHE because the dcp node is not dma-coherent.

- G5: there is a third sub-mechanism that no hypothesis states explicitly, (c): the locked iBoot L1 page that the hardware walks differs from the kernel L1 at slot 0x7ff. Linux writes the locked L1 only in apple_dart_hw_sync_locked (apple-dart.c:487-495), so a difference at fault time with no Linux sync in between means another agent wrote it. The ADT gives dart-dcp 'l2-tt-5' (2 iBoot-built L2 tables) and 'pt-region-5', which hints that firmware may manage sid5 tables (inference). This is decidable only by reading locked_ttbr[5][0][0x7ff] at the fault. Note: /proc/kcore (drgn or gdb) cannot read that page. It is memremap'd outside Linux RAM and so becomes VM_IOREMAP, and vread_iter zero-fills it (mm/vmalloc.c:4772-4775). It has to be a kprobe fetch or an in-kernel print.

- G6: determinism is unknown. Only one DPMS-off has ever run on 7.2.2-fay-dcp (boot -3; journalctl --list-boots). The control boot never ran dcp_poweroff. Still open: does every setPowerState(0) crash, only the first one, or does it depend on uptime? The crash came about 6 min after boot.

- G7: the DCP crashlog was only partly decoded. Sections 0x43637374 'Ccst', 0x4372746b 'Crtk', 0x43617343 'CasC', 0x43636470 'Ccdp' and 0x43737461 'Csta' were printed only as 'Unknown crashlog section' (crash-boot.log:1103-1104 and nearby). There was no Cstr section. These sections may hold the cause, the fault address or a backtrace. dcp_rtk_crashed (dcp.c:251) receives the shadow copy (rtkit.c:385-397) and discards it. Post-crash, the buffer is likely still readable at PA 0x103e1aa6000 (crash-boot.log:705; inferred to be the crashlog endpoint).

- G8: the faulting instruction is not identified. DCP PC 0x20e158 has not been disassembled. That needs the exact 14.8.3-stub DCP firmware, from the stub APFS container or from IPSW 23J220. The firmware also contains the D-number/name table, which would close G3.

- G9: two inferences about the fault itself are unverified. (i) 'Posted store to a register': the DCP SError may be DART error reflection, not a bus error from the store. The ADT dart-dcp has 'error-reflector' = <0x7f000000 0x2>, i.e. a reflection target at PA 0x27f000000 (my reading of the property). Only WRITE_nREAD (bit 28) actually shows a write. (ii) 'First stream-5 access to the dashboard page at power-down': Linux cannot observe successful DART walks, so whether the DVA was ever used at power-up (set_run_mode 2->4, program_M3_rt_config at 23:09:57.604879) is unknown.

- G10: power-domain activity in the 20 ms window was not logged. ps_disp_cpu (dcp, dcp_dart and mailbox all sit in it; t8122.dtsi:951/966/983) is NOT always-on; it has 'apple,min-state = <4>' (t8122-pmgr.dtsi:1117-1125). Linux genpd gating is unlikely while dcp is bound, but it is unproven. A kprobe on apple_pmgr_ps_set excludes it.

- G11: DART bit 18 (m1n1 name 'FILL_REGION') has no known meaning. Also unexplained for dart-dcp: 'dart-options' = 0x65, 'flush-by-dva' = 0, 'retention' and 'retention-force-quiesce' (fay-display-nodes.txt). These are relevant to sub-mechanism (a), a TLB/prefetch/flush issue. The local stub kernelcache (/boot/asahi/kernelcache.release.mac15g, im4p-compressed) could be decompressed and its AppleT8110DART strings grepped for error-bit names.

- G12: macOS behaviour at DISPLAY sleep is unknown. Does macOS reach 'set_run_mode ... 1 -> 0' and 'power_down_M3: disabling M3' on display sleep, or only on system sleep? This decides whether the 'skip setPowerState(0) on DPMS-off' robustness fix matches macOS behaviour.

- G13: the Linux-boot carveout map is unknown. The macOS ADT region addresses differ from the stub boot (crash-boot.log:13 dcp_data@103e1864000 vs macOS region-id-50 0x103e1950000). The stub boot's /chosen/carveout-memory-map is needed only for H1(b) (stray physical write via bypass-15). It must come from m1n1 (ADT dump at boot), not from macOS.

- G14: why PR #607 gives per-master DMA windows for t6030 is unexplained (dcp: '<&dcp_dart 5 0x100 0x0 0x10 0x0>'; dcpext1 restricted to '<... 0x0 0xf0000000 0x0 0x0f000000>'), while t8122 uses 'apple,dma-range' on the DART node (t8122.dtsi:952). It could mean firmware-reserved DVA ranges exist (inference, low priority).

- G15 (practical blocker): /usr/lib/modules/7.2.2-fay-dcp no longer exists. Only 7.1.13-3-2-ARCH and an empty .old remain. appledrm.ko is NOT in initramfs-fay-dcp.img (lsinitcpio: 196 modules, none from drm/apple), so booting fay-dcp now would never load appledrm. The cause is linux-modules-cleanup.service (enabled). On every boot it rsyncs to .old and deletes any module dir that is neither the running kernel nor pacman-owned. It will delete the tree again after every return to linux-asahi. Also: drgn, bpftrace, trace-cmd and perf are not installed (gdb is), so the drgn walk in H1's decisive test cannot run as written. And root is LUKS (cryptdevice= on the cmdline), so every boot needs the user to type the passphrase.
